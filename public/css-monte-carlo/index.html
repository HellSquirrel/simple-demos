Every piece of confetti is an empty <i> element. CSS throws it to a random position, checks whether it's inside or outside the circle, and counts the hits. BTW, this demo is JavaScript-free. Doing maths in JavaScript would be very boring.

How CSS throws fresh confetti on each click

Fresh confetti on every click

A piece keeps its random values for life, so the button can't simply re-roll them. Instead, it cycles through ten hidden radio inputs. Clicking a label checks the next one - HTML handles that for us - and CSS uses :has() to turn the checked radio into a number s from 0 to 9.

Each piece keeps two random numbers, u and v, and flies to mod(u + s·v, 1). Two different values of s give two independent positions, so every throw looks new. Even states draw the confetti in ::before, odd ones in ::after. A brand-new pseudo-element plays its animation from the start, so the confetti flies again. 

body:has(#c-1:checked) { --s: 1; }   /* … up to 9 */

  .confetti i::before,
  .confetti i::after {
    --cx: calc(300px * mod(random(--cx element-scoped, 0, 1)
             + var(--s) * random(--cx2 element-scoped, 0, 1), 1) - 150px);
  }
  body:has(.ev:checked) .confetti i::before,
  body:has(.od:checked) .confetti i::after { content: ""; }

After ten clicks the confetti repeats. Chrome hides that by giving a recreated pseudo-element fresh values; Safari keeps the old ones.

Congratulations, you just did Monte Carlo integration

Estimating things with random samples is called the Monte Carlo method.

Why Monte Carlo?

In 1946 the mathematician Stanisław Ulam was recovering from an illness, playing a lot of solitaire, and wondered how often a game can be won. The odds were too hard to calculate, so he figured it was easier to deal a few hundred games and count. John von Neumann turned the idea into a program that simulated neutrons at Los Alamos, and Nicholas Metropolis named it after the casino in Monaco: Ulam's uncle used to borrow money from relatives because he “just had to go to Monte Carlo.”

A thousand pieces, one estimate

Now let's estimate an integral. We'll scatter a fixed batch of confetti across a box and use the fraction below the curve to estimate its area.

Take a nonnegative function over an interval and draw a box around the area beneath it. Throw confetti across the box, count the fraction below the curve, and multiply by the box's area. That gives us an estimate of the definite integral.

Below, a thousand pieces of confetti try four functions. We've shrunk them to fit; they're at work now. The first is our quarter circle, stretched vertically by four. Two others, the bell curve and the sophomore's dream, have no elementary antiderivative. The confetti doesn't care.

How CSS places, checks and counts the thousand pieces

Where a piece lands

Each piece needs two coordinates. We need to use the same numbers to position it and check whether it landed inside the curve. Otherwise, we'd be counting one throw and drawing another.

A custom property doesn't store a random number - it stores the text random(0, 1), and every var(--x) rolls again. Unless the roll has a name: random(--x element-scoped, 0, 1) gives every property of one piece the same value, and every piece its own: 

.pieces i {
    --x: random(--x element-scoped, 0, 1);
    --y: random(--y element-scoped, 0, 1);
    left: calc(var(--x) * 100%);
    bottom: calc(var(--y) * 100%);
  }

Each piece gets its own coordinates. The throw you see - the confetti flying, the pieces dropping onto the plot - is a short CSS animation that ends at those coordinates. Replaying the animation doesn't give the piece new ones, though. Throwing the same piece again takes a little more work.

Inside or outside

For the unit circle, a piece is inside when x2+y2<1. For the other curves, we map the piece's horizontal coordinate onto the integration interval, calculate the function's value there, and compare it with the piece's height.

CSS has the maths we need: sqrt(), sin(), exp() and pow(). Taking sign() of the function's value minus the piece's height gives 1 below the curve, 0 on it, and -1 above it. max(0, …) turns this into 1 for a hit and 0 for a miss: 

--u: calc(var(--a) + (var(--b) - var(--a)) * var(--x));
  --f: exp(-1 * var(--u) * var(--u));          /* the bell curve */
  --hit: max(0, sign(var(--f) - var(--H) * var(--y)));

  background: color-mix(in oklab, var(--hit-c) calc(var(--hit) * 100%), var(--miss-c));

Choose another function and CSS checks the same thousand pieces against the new curve. Their positions in the plot stay the same; the function, interval and box height change.

Counting and displaying the estimate

CSS counters add up the contributions from each piece. With 100 throws and a box area of 4, each hit adds 4 / 100 = 0.04 to the estimate.

Counters only store whole numbers, so we multiply everything by 100 000 000. Each hit adds 4 000 000. After 78 hits, the counter holds 312 000 000, which represents 3.12. An unnecessarily large integer, but a perfectly reasonable estimate of π. 

/* a hit is worth A / 100, in units of 10⁻⁸ */
  --w: calc(round(var(--hit) * var(--A) * 1e6));
  counter-increment: estimate var(--w);

The table repeats this calculation for the first 10, 100 and 1 000 pieces. Each hit contributes A/N, where A is the box's area and N is the number of throws.

Another counter tracks the error. It starts at the negative of the known integral, scaled up by the same factor. Adding the hits leaves us with the estimate minus the known answer.

The typical-error column uses I(A−I)/N, where I is the known integral. This gives the standard error for independent, uniformly distributed throws. CSS calculates it in counter-reset. It doesn't use the actual hits - this column describes how the method behaves across repeated runs.

@counter-style pads the counter to nine digits. For example, 314159265 represents 3.14159265. We display it twice: one copy is clipped to show the first digit, and the other is shifted and clipped to show the next four. Put a decimal point between them and we get 3.1416 (thanks to the rounding below).

The estimate counters start with an extra 5 000, equivalent to 0.00005, so clipping to four decimal places rounds the estimate instead of truncating it.

One piece, a running estimate

A thousand pieces seems excessive. Let's reuse one. This time, we want the estimate to keep updating as new throws arrive. The next panel throws one piece of confetti ten times a second and keeps a running score.

Two CSS animations act as stopwatches. One measures all the time that passes; the other runs only while the confetti is below the curve. Each position lasts the same amount of time, so the fraction of time below the curve gives us the fraction of throws that hit. Multiply by the box's area, just as before, and we have our running estimate.

How CSS generates the sequence and runs the stopwatches

Throwing one piece, again and again

The continuous sampler needs a new position every 100 ms. Putting random() inside @keyframes doesn't give us a fresh number on every loop. Instead, we give random values names and use animations to cycle through them.

A call like random(--g1-17, 0, 1) gives a random value a name. Using that name elsewhere with the same range gives us the same value. Three step animations cycle through lists of named random values: g1 has 97 values, g2 has 89, and g3 has 83. Each advances one entry every 100 ms.

One short list would repeat too soon. No two of these list lengths share a factor greater than 1, so their positions line up again after 97 × 89 × 83 = 716 539 throws - nearly twenty hours.

To get x, we add the current values from g1 and g3 and keep the fractional part. For y, we add g2 and g3. In CSS, that's mod(var(--g1) + var(--g3), 1) for x, and the same expression with --g2 for y. 

@keyframes g1 {
    0%       { --g1: random(--g1-0, 0, 1); }
    1.03093% { --g1: random(--g1-1, 0, 1); }
    /* … 95 more … */
  }
  .engine {
    animation: g1 9700ms step-end infinite, g2 8900ms step-end infinite,
               g3 8300ms step-end infinite;
    --x: mod(var(--g1) + var(--g3), 1);
    --y: mod(var(--g2) + var(--g3), 1);
  }

Fifty elements draw the trail. They run the same sequence with staggered delays, so each marks an earlier landing. New marks fade in with a ring; older marks gradually disappear.

Keeping score with animation time

Two CSS animations act as stopwatches. One runs continuously; the other runs only while the confetti is below the curve.

How does the second one know? --hit is still the text max(0, sign(…random(…)…)), so a container style query would only compare text. But a width can be measured: the stopwatches sit inside a box that is 2px wider during a hit, and a container size query resumes the second animation. Divide its elapsed time by the first stopwatch's time, then multiply by the box's area to get the estimate: 

.gate {
    container: gate / inline-size;
    width: calc(15rem + var(--hit) * 2px);
  }
  .tally {
    animation: clk 100000s linear infinite, acc 100000s linear infinite;
    animation-play-state: running, paused;
  }
  @container gate (width > 15.05rem) {
    .tally { animation-play-state: running, running; }
  }

  --est: calc(var(--A) * var(--acc) / var(--clk));

Why it is so slow

For independent throws, the standard error shrinks as 1/N. Making it ten times smaller takes a hundred times as many throws. At ten throws a second, collecting 10 000 samples takes about seventeen minutes. Confetti is not in a hurry.

For these one-dimensional integrals, other numerical methods are usually much faster. Monte Carlo becomes useful in higher dimensions, where adding grid points along every axis quickly gets expensive. Its 1/N convergence rate still holds for independent samples with finite variance, though the variance depends on the problem.

A stylesheet remains an unusual place to do this. 😉
