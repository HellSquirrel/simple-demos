A JS-less Neural Network on… Scrollbars

Modern CSS has superpowers: real trigonometry, exponents, custom functions, even conditionals via if(). Two things it famously does not have: loops, and variables you can update.

So, is CSS cool enough to train a neural network anyway — actually train it, run the training loop, without a single drop of JavaScript? Let’s give it a try.

The goal

Teach a goldfish to swim with grace — that is, to follow a pre-defined trajectory across the tank. Three ingredients required:

  • training data — sixteen positions in the tank, and a teacher (species: 🐟) who demonstrates the correct height at each of them;
  • a neural network — the math that predicts the student’s height from its position;
  • training mechanics — the machinery that compares student to teacher and updates the network’s parameters until the student follows.

That is the whole attempt, and it is already running. The three scrollbars are the three parameters of a tiny neural network, training right now: one optimizer step per frame, momentum and all, forever. Their scroll positions are the network’s memory; the rendering loop is its clock; mandatory snap is the optimizer’s hand. If the green curve hugs the wave when you arrive, it’s because the scrollbars bent it there on their own, moments ago. Grab one and fight it.

Two challenges

Two things stand between a stylesheet and a training run: the loop and the update.

The loop is traditionally faked by unrolling: hardcode every iteration, a fixed number of times, in CSS or in the DOM — say, eighty nested <div>s, each computing one step from its parent’s values. It works, it’s even fast, but it trades time for space, and it ends: step eighty-one does not exist, and the step count is written into the markup like a prophecy. We want true recursion — the next state computed from the previous one, indefinitely, with no iteration count written anywhere.

The update is harder still: CSS forbids a variable from being defined in terms of itself. Both problems, it turns out, have the same unlikely solution.

The parameters are scrollbars

To simulate variable assignment, we store the variables in scrollbars — precisely, in scroll positions. How far each one is scrolled is the number. It’s the one continuously-valued piece of state the browser keeps between frames that a stylesheet can both read and write: a scroll-timeline reads the position back as a number, plain calc() does the arithmetic, and scroll-snap-type: mandatory does the writing — the scroller must sit wherever its only snap target is, so parking that target somewhere is the assignment. Read, compute, write. The browser’s frame loop is the for loop. 

.reg.v0 { scroll-timeline: --t0 y; }   /* read port  */
.reg.v0 .pull {                        /* write port */
  scroll-snap-align: start;            /* mandatory snap = assignment */
  animation: read-v0 linear both, …;   /* read last phase’s params   */
  animation-timeline: --t0s, --t1s, --t2s, --m0s;

  /* …the optimizer’s calc() lives here — the exact lines wait
     for you in “How it plays together”, at the end… */
  top: calc((var(--v0) + 4) * 118.75px + var(--vel-next) * 1px);
}

The gradient bar inside each register is the write port: it sits at that parameter’s next value, and snap drags the scroller onto it — including while you’re scrolling the other way. Your thumb is competing with a layout constraint. The constraint has more stamina.

Nothing in the update is pre-computed. The stylesheet stores the sixteen sample positions as variables and two hyperparameters — that’s the optimizer’s entire allowance. Labels aren’t even stored: --teacher(x) asks sin() at runtime. Residuals, gradient, and the per-weight curvature used as a step size are all computed by calc() from those, every frame; the optimum emerges when the gradient runs out. Momentum is not decoration either: this loss has a nearly-collinear valley, and the velocity registers (six more scrollers you can’t see) work as sub-pixel accumulators — tiny gradients pile up in velocity until they’re big enough to move a whole pixel of parameter. And the gradient is coupled: pin one parameter somewhere stupid and the other two renegotiate around the injury, which is the most lifelike thing a scrollbar has ever done.

The clock

And the clock — the one part of a loop CSS never had — turns out to cost nothing, because the browser already has one. Every frame it re-renders: animations resample their timelines, layout re-places the snap targets, snap re-asserts the scroll positions. That is the iteration. Nothing ticks the machine; being rendered is being ticked. The training loop is the render loop.

One wrinkle: Chrome refuses to run a scroll-driven animation that scrolls its own scroller. Fair — that’s a layout cycle. It has no opinion, however, about an animation that scrolls somebody else’s scroller. So every parameter has a hidden shadow register that copies it, and parameters read only shadows: a two-phase flip-flop — primary and shadow — 1950s technology rebuilt from overflow: scroll. One optimizer step per copy-then-compute cycle, forever.

The tank

The tank, for once, is just a little animated CSS — the only ordinary part of this page. The 🐟 swims sin(x), which CSS knows natively (an unfair advantage in a teacher). The goldfish 🐠 rides the network’s curve — three line segments, exact formula at the end of the page — drawn live in green with parameters read straight off the registers; the red bar is the current error.

The scoreboard doesn’t cheat

The loss readout is not a caption. calc() recomputes the sixteen-point mean squared error from the live parameters every frame — sixteen pow()s and a division — and the digits reach the screen through counter(), the only mechanism by which CSS permits a number to become text. Sabotage a parameter and watch it spike.

How it plays together

A little math inside — but it’s nice and simple. The fish’s horizontal position x sweeps across the tank on a loop; its vertical coordinate is whatever the network says it is:

y(x) = v0·x + v1· relu(x−14) + v2· relu(x−34)

Here relu(t)= max(0,t) — a hinge: zero until its threshold, a straight line after. So the whole curve is three line segments, and the three numbers v0, v1, v2 are the parameters we are going to train: v0 sets the opening slope, v1 bends it at the crest (x=14), v2 bends it back at the trough (x=34). The teacher’s coordinate is sin(2πx); training means making the two functions agree at the sixteen sample positions.

On every iteration of the training loop — which here means: on every rendered frame — we calculate our y at each sample position and compare it with the teacher’s answer:

ri = y(xi) − sin(2πxi)

These sixteen residuals are the whole story of how wrong we are. Squared and averaged, they become the loss on the scoreboard. Weighted by each parameter’s own feature and averaged, they become the gradient — the direction that would make things worse, so we go the other way:

ga = 2N ∑i φa (xi) · ri

(φa is simply the thing parameter a multiplies in the formula above: x, or one of the two hinges.) Then each parameter takes a small step downhill, with momentum:

ma ← β·ma − γ· ga Ha , va ← va + ma

ma is the parameter’s velocity — the momentum that makes the fish overshoot and ring instead of gliding politely. β=0.985 is inertia, γ=0.02 is caution, and Ha is a per-parameter scale computed from the same sixteen positions, so steep features get gentler steps.

And here is that optimizer in CSS, piece by piece — shown for v0; the other two differ only in indices. First, the register itself: a plain scroller. Its scroll position is the parameter. scroll-timeline publishes that position for anyone to read, and mandatory snap obliges the scroller to sit wherever its snap target is — which is how it will be written to: 

.reg.v0 {
  scroll-timeline: --t0 y;
  scroll-snap-type: y mandatory;
}

The read happens via animations. Inside the register sits its write target — .pull — running four scroll-driven animations. Each one samples a register from the previous phase (the shadows) and delivers its value to calc() as a plain number: the three parameters and this parameter’s velocity. 

animation: read-v0 linear both, read-v1 linear both,
           read-v2 linear both, read-vel linear both;
animation-timeline: --t0s, --t1s, --t2s, --m0s;

The compute is the three formulas, transcribed: the sixteen residuals, the gradient, the momentum step (the 118.75 just converts parameter units to rail pixels): 

--r1: calc(--net(var(--x1)) - --teacher(var(--x1)));
/* … --r2 through --r16 … */

--g0: calc((var(--x1)*var(--r1) + var(--x2)*var(--r2)
        + … + var(--x16)*var(--r16)) / 8);

--vel-next: clamp(-40, calc(var(--beta) * var(--vel)
        - var(--gamma) * var(--g0) / var(--H0) * 118.75), 40);

And the write is geometry. The freshly computed next value becomes this element’s position, and scroll-snap-align makes it the register’s one snap target — so the mandatory snap declared above drags the scrollbar onto it. That drag is the assignment, v0←v0+m0, executed by the layout engine: 

top: calc((var(--v0) + 4) * 118.75px + var(--vel-next) * 1px);
scroll-snap-align: start;

That is the entire optimizer: sixteen subtractions, three weighted sums, momentum, step — once per frame, forever. The scrollbars do the rest.
